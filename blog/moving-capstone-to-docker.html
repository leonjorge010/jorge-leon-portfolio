Moving Our Capstone to Docker

Part of Autonomous Navigating Robot

Overview

I am suggesting that we move our embedded systems capstone workflow to Docker. This would give the entire team one consistent environment to build and test our autonomous navigating robot, instead of having everyone work directly on their own machines or on the Jetson itself.

The problem

We've been working on the Jetson like a regular computer using a monitor, keyboard, mouse, etc. While that works, it's inefficient and isn't always practical. The Jetson is stored away when we're not actively using it, and we don't want to be tied to campus just to make progress. We could SSH into the Jetson, but we would still need to be on the same LAN unless we set up additional remote-access infrastructure. On top of that, since we're all developing on our own machines, we may run into runtime errors because one teammate's dependency versions, operating system, or hardware setup doesn't match another's. This means that code that works for one person may break for someone else.

The solution

Docker would give us a standardized development environment that can run consistently across our different machines. Everyone would build from and work within the same Docker image, which would contain the project's dependencies, libraries, tools, and configuration. This would make our development environment reproducible and significantly reduce differences between teammates' setups. It would also allow us to work on the project from our own computers without needing constant physical access to the Jetson. Docker provides isolation between the project environment and the host machine, making it easier to maintain consistent dependencies and avoid conflicts with other software installed on our computers.

Challenges

I don't think any of us have used Docker before, so there will be a learning curve to manage. The goal would be to keep that learning curve shallow by having me set up the initial image and workflow so teammates only need to learn a few basic commands to pull, run, and build inside the environment. We'll also need to make sure the containerized environment reflects the Jetson's software and hardware constraints closely enough that development in Docker translates reliably to the actual device.

Current state

There is no adoption yet. This week, I’ll test the Docker-based workflow to see if we can make as much progress working through the containerized environment as we have with our current setup. This should give us a better idea of whether Docker can realistically support our day-to-day development without creating additional obstacles. After testing it, I’ll give another update with the results and any changes we may need to make before adopting it as a team.
